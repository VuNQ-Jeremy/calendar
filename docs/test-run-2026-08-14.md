### FINDING 1 — cloze/listen example matching is substring, not whole-word (APP-SIDE, pre-existing, NOT fixed)

All four unit failures share one root cause.

Failing tests:
- `test/flashcard-games.test.ts` → `blankExample / exampleEligible > is ineligible when the sentence does not contain the answer`
- `test/flashcard-games.test.ts` → `buildClozeQuestions > only asks words with a usable sentence, and the answer is a real option` (got `['1','2','3','5']`, expected `['1','2','3']`)
- `test/vocab-enrich.test.ts` → `sanitizeEnrichedWords > nulls BOTH example fields when the sentence does not contain the answer`
- `test/vocab-generate.test.ts` → `sanitizeGeneratedWords > nulls BOTH example fields when the sentence does not contain the answer`

**Root cause.** Three code paths test "does the sentence contain its answer?" with a plain
case-insensitive substring search:
- `shared/logic/flashcards.ts:388` — `exampleAnswerIndex` uses `sentence.toLowerCase().indexOf(answer.toLowerCase())`
- `server/services/enrich.ts:133` — `exampleEn.toLowerCase().includes(exampleAnswer.toLowerCase())`
- `server/services/generate.ts` — same shape in `sanitizeGeneratedWords`

Substring matching accepts an inflected mismatch: answer `run` is "found" inside sentence
`He runs fast.` at index 3. The tests assert whole-word matching.

**Why the tests are right and the code is wrong.** The enrich/generate prompt
(`server/services/enrich.ts:23-24`) instructs the model to return `exampleAnswer` as *the exact
form as it appears in exampleEn — copy it character for character, including any inflection
("ran" for "run")*. A substring-only hit is exactly the signal that the model failed to do that.
Accepting it produces a broken cloze: word `read` with sentence `He reads books.` and answer
`read` renders as **"He _____s books."** — the test fixture at
`test/flashcard-games.test.ts:330` is literally commented `// mismatched form`, and it currently
leaks into the question set (that is the `'5'` in the second failure).

**Pre-existing, not a regression from this run.** `git log -S` shows `exampleAnswerIndex` and the
assertion string `He runs fast.` were both introduced by the same commit `0d7f097`
(*feat: 5 new vocabulary games + AI example sentences*), and no word-boundary regex has ever
existed in `shared/logic/flashcards.ts`. These four tests have been red since they were written.

**Proposed fix (NOT applied — app logic is plan-only per this run's policy).**
Make the containment check word-boundary aware in one shared helper and have both sanitizers use
it, rather than fixing three copies independently:

1. In `shared/logic/flashcards.ts`, change `exampleAnswerIndex` to require boundaries around the
   match — scan candidate indices from `indexOf` and accept one only when the characters either
   side are non-word (or string edges). A regex built from an escaped answer works too, but the
   answer is model-supplied text, so escape it (`replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`) or the
   first answer containing punctuation throws.
2. Export a small `exampleContainsAnswer(sentence, answer)` from the same module and call it from
   `sanitizeEnrichedWords` and `sanitizeGeneratedWords` in place of their local `.includes()`.

**Blast radius.** `exampleAnswerIndex` feeds `exampleEligible` → `wordsWithExamples` →
`buildClozeQuestions` / `buildListenQuestions` and `wordSupportsMode` for the mixed round
(`shared/logic/flashcards.ts:688-690`); `shared/` is consumed by web **and** mobile, so the change
ships to both. Effect is strictly *narrowing*: some cards stop being offered in cloze/listen/mix.
Decks whose AI-filled examples are mostly inflected mismatches could drop below `MIN_WORDS.cloze`
and lose the mode entirely — worth a check against real data before shipping. The sanitizer half
only affects newly enriched/generated words; rows already stored with a mismatched pair stay in
the database and still need the game-side guard, which is why fixing both halves matters.

### FINDING 2 — the dashboard's "today" is UTC, so early-morning ICT loses one-off events (APP-SIDE, NOT fixed)

**Symptom.** Created an event on the phone for today (2026-08-14, 09:00, no class). It saved and
the Calendar tab shows it correctly under a "Today 14 Aug" heading — but the Dashboard kept
reading **"Nothing scheduled today"**, before and after a pull-to-refresh.

**Not a cache bug — the server never sent it.** `GET /api/dashboard` at 02:47 ICT returned:

```
"today":"2026-08-13"          <-- server
UTC now: 2026-08-13 19:47  |  local now: 2026-08-14 02:47
contains "Mobile QA event"? 0
```

**Root cause.** `app/routes/api.dashboard.tsx:13` computes `const today = iso(new Date())`.
Cloudflare Workers run in UTC, but the school is ICT (UTC+7), so between **00:00 and 07:00 local
time the server's "today" is still yesterday**. `eventsSvc.listForToday` then selects
`date = todayIso OR recurrence != 'none'` (`server/services/events.ts:180-185`), which drops every
non-recurring event dated to the real local day. The client compounds it: `dashboard.tsx:60` runs
`eventsOn(todayEvents, todayDate())` against the DEVICE's date, so the recurring rows the server
did return are filtered out too — during that window the card is reliably empty rather than merely
incomplete.

**The codebase already has the right helper.** `server/services/notify.ts:44` exports
`ictNow(at)` (`ICT_OFFSET_MIN = 7 * 60`, "Now, as the school experiences it"), and
`shared/logic/preview.ts` / `shared/logic/tests.ts` each define the same offset. The dashboard
loaders simply do not use it.

**Both dashboards are affected**, not just mobile — `app/routes/dashboard.tsx:24` computes
`const today = iso(now)` and calls the same `listForToday`. Those are the only two callers.

**Proposed fix (NOT applied — app logic is plan-only).** Replace `iso(new Date())` with the ICT
day in both loaders, e.g. `ictNow(new Date()).dateIso`. Lifting `ictNow` (and the duplicated
`ICT_OFFSET_MIN`) into `shared/logic/dates.ts` would stop the fourth copy from appearing. Also
reconsider the client-side `eventsOn(..., todayDate())` filter: with an ICT-correct server day the
device filter is redundant, and on a device whose clock or timezone differs it silently re-creates
this same class of bug.

**Impact.** Every morning before 07:00 ICT a teacher opening the app sees an empty "Today's
schedule" — the exact "two taps from cold launch to marking a register" flow the file header calls
the whole point of the phone app.
