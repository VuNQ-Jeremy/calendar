# Whole-codebase review — plan

_Written 2026-08-14. Plan only — nothing here has been executed._

A full review of Mochi's ~120,000 lines of TypeScript. This document is the **how**:
what to review, in what order, with what brief, and what each slice must produce. An
executor (engineer or agent) should be able to run any single slice from this file
alone, without reading the others.

> **Why this isn't `/mattpocock-skills:code-review`.** That skill diffs `HEAD` against a
> fixed point and reviews only the changed hunks. A whole-codebase review has no fixed
> point — every line is in scope. This plan borrows the skill's best idea (two
> independent axes, reported side by side, never merged) and applies it to slices of the
> tree instead of hunks of a diff.

## The two axes

Every slice is reviewed along two axes that are **reported separately and never merged
or reranked**. A slice can pass one and fail the other, and letting one mask the other
is the whole failure mode this separation exists to prevent.

### Axis A — Standards

Does the code follow this repo's documented conventions?

**Documented sources**, in precedence order (a repo standard always beats the baseline):

1. `CLAUDE.md` — git/versioning/OTA/e2e/testing rules
2. `README.md` — repo layout and the stated architectural contracts
3. `CONTRIBUTING.md`
4. `docs/mobile/README.md` — repo orientation for the mobile side
5. `AGENTS.md`, `CONTEXT.md` if present at the reviewed path
6. `.oxlintrc.json`, `.prettierrc` — **skip anything these already enforce**

**Repo-specific hard contracts** (breaches of these are hard violations, not judgement calls):

- Route files in `app/routes/` are **thin**: a loader, an action, a re-export of a screen
  from `src/`. Domain logic in a route file is a violation — it belongs in
  `server/services/`.
- **Nothing lives in route files**; both clients go through `server/services/`.
- Every user-facing string goes through `t(key)` with an entry in **both** `en` and `vi`
  in `shared/i18n/strings.ts`. A hardcoded string is a violation.
- `server/db/schema.ts` is the single source of truth for the schema.
- Zod contracts in `shared/schemas.ts`; client forms and types **infer** from them rather
  than restating shapes.
- Trust boundary rule (from `REFACTOR_PLAN.md`): trust / scores / persistence → server;
  pixels → client. Anything mintable or scoreable in the browser is a violation.
- The build number is derived from the git commit count and is **never** stored or
  hand-edited; `shared/version.json` holds only `major`, `buildOffset`, `runtimeVersion`.

**Smell baseline** (Fowler, _Refactoring_ ch.3). Always applies, even where the repo
documents nothing. Always a **judgement call** — label it "possible X", never a hard
violation — and always overridden by a documented repo standard. Skip anything tooling
enforces.

- **Mysterious Name** — name doesn't reveal what it does or holds → rename; if no honest name comes, the design's murky.
- **Duplicated Code** — same logic shape in more than one place → extract, call from both.
- **Feature Envy** — a method reaching into another object's data more than its own → move it onto the data it envies.
- **Data Clumps** — the same few fields keep travelling together → bundle into one type.
- **Primitive Obsession** — a primitive or string standing in for a domain concept → give the concept its own small type.
- **Repeated Switches** — the same `switch`/`if`-cascade on the same type recurs → polymorphism, or one shared map.
- **Shotgun Surgery** — one logical change forces scattered edits → gather what changes together.
- **Divergent Change** — one module edited for several unrelated reasons → split so each changes for one reason.
- **Speculative Generality** — abstraction or hooks for needs nothing has → delete, inline back.
- **Message Chains** — long `a.b().c().d()` the caller shouldn't depend on → hide behind one method.
- **Middle Man** — a class or function that mostly delegates → cut it, call the target direct.
- **Refused Bequest** — a subclass ignoring most of what it inherits → composition instead.

### Axis B — Correctness

Does the code do the right thing? With no per-feature spec to diff against, Axis B asks
three questions instead:

1. **Contract drift** — does the implementation match its Zod schema in
   `shared/schemas.ts` and its declared shape in `shared/api-contract.ts`? Does the
   OpenAPI registry in `server/api/docs/registry.ts` match what the handler actually
   returns?
2. **Invariant breaks** — bugs findable by reading: unhandled `null`, wrong timezone
   (ICT vs UTC — there is git history of exactly this bug), off-by-one in date/recurrence
   maths, non-atomic multi-write paths that should be in a `db.batch`, money arithmetic
   in floats.
3. **Documented-behaviour mismatch** — where `docs/` states a behaviour, does the code
   do it? **Where they disagree, suspect the doc** (see Slice 0).

## Slice 2 — Money and grading

**Wrong numbers here reach parents.** Small, dense, high-consequence.

**Files:**

```
server/services/tuition.ts       shared/logic/tuition.ts
server/services/fee-slip.ts      shared/logic/fees.ts

```

**Axis B brief, specifically:**

- **Float money.** Any currency held as a JS `number` and summed is a finding. VND has no
  minor unit, which makes this *less* dangerous than most currencies — but check
  proportional/pro-rata discount paths, which are where fractions enter.
- **Rounding.** Where a percentage or average is rounded, is the rule stated once and
  shared, or restated per call site with different behaviour?
- **Timezone.** Billing periods and assessment windows must use the **ICT day**, not the
  Worker's UTC day. Commit `879e584` fixed exactly this bug on the dashboard — check
  whether the same mistake exists in the billing and grading paths.
- **Atomicity.** Multi-write paths (issue a slip, record a payment, publish a report card)
  belong in a `db.batch`. `BACKEND.md` claims phase-5 verified this "across all
  multi-write paths" — verify that claim against the services added since.

## Slice 5 — `app/routes/` thinness

120 files, 7,158 lines — an average of 60 lines per route, which is consistent with the
thin contract. This slice is **mechanical**: verify the contract holds and find the
outliers.

**Method:**

1. Rank all 120 route files by line count. Anything materially above the ~60-line mean is
   a candidate.
2. For each candidate, ask: is the extra size a loader/action pair with real domain logic
   inline? If yes → **hard violation** of the stated contract, and name the
   `server/services/` module it belongs in.
3. Check `app/routes.ts` (explicit route config, not file-based) against the files on
   disk — orphaned route files that nothing references are dead code.
4. `app/root.tsx` owns "the whole document head" — check nothing else writes head tags.

**Output:** `docs/review/05-routes.md`.

## Slice 6 — `src/` web UI

Largest slice, ~30,500 lines, lowest per-line risk. Budget accordingly — this is the one
to shorten if time runs out.

**Order within the slice, largest-first:**

```
src/screens-config.tsx        1,727    ← largest non-generated file in the repo
src/flashcards/               5,978    topic.tsx alone is 1,266
src/garden/                   2,383
src/calendar/                 2,139    event-modal.tsx is 861
src/screens-manage/           1,602    people.tsx is 1,082
src/screens-assessments.tsx   1,120
src/screens-extra.tsx           926
src/tuition/, src/lib/, src/components/, src/ds/ (excl. bundle.js),
src/preview/, src/kiosk/, src/parent/, src/schedule/, src/tui-mu/
```

**Axis A brief, specifically:**

- **Hardcoded strings.** `npm run check:i18n` proves every `t()` key exists in both
  languages — it does **not** prove every user-facing string goes through `t()`. Grep for
  string literals in JSX text positions and in `aria-label`, `placeholder`, `title`.
  `docs/i18n-unused-keys.md` covers the opposite direction; this is the gap.
- **File size as a smell.** A 1,727-line `screens-config.tsx` is prima facie Divergent
  Change — name the distinct reasons it changes.
- **The remount hazard.** `CLAUDE.md` documents it: creating a new component function on
  every parent render (`React.createElement(() => <Child />, ...)` with a fresh arrow each
  time) unmounts and remounts the whole subtree, wiping local state. Grep for inline
  component definitions inside render paths — this bit the repo before.
- **Cache invalidation.** `src/lib/` holds the client route cache (`cache.ts`,
  `clientLoader`/`clientAction`, `useCachedLoad`). Every mutation must invalidate the keys
  it dirties. A missing invalidation is a stale-UI bug, not a style issue.

**Output:** `docs/review/06-web-ui.md`.

## Slice 8 — Test suite honesty

24,177 lines across `test/` (7,390), `test-worker/` (7,336), `e2e/` (5,041) and
`src/tests/` (4,410) — a fifth of the codebase. **Review by reading. Do not run.**

**The question is not "do tests exist" but "would they fail if the code broke".**

**Axis A brief:**

- `CLAUDE.md`: every new feature, mutation intent, or data object ships with an e2e spec
  **in the same commit**. Walk the route action intents and the dialogs, and list which
  have no matching lifecycle test in `e2e/crud-*.spec.ts`. The stated contract is that
  every write path is exercised end to end.
- Specs must use the helper kit in `e2e/crud-helpers.ts`, which encodes the UI contract:
  no `<form>`/`name=` attributes (locate inputs structurally by `.mochi-field` label),
  combobox/date menus portalled to `document.body` (locate options from `page` with exact
  names), and dialogs that close optimistically before the server responds (always
  `await posted(path)` before asserting on the re-rendered list). A spec that hand-rolls
  these is a finding — it will flake.
- **Reset sweep completeness.** `seed.sql` predates several tables, so
  `scripts/test-accounts.sql` deletes them explicitly. Cross-reference every table in
  `server/db/schema.ts` and in `migrations/` against the `DELETE FROM` list. A missing
  entry leaks rows into the next reset — this is a real, recurring failure mode, and the
  single highest-value check in this slice.
- CRUD specs are guarded in `e2e/crud-helpers.ts` and skip unless `E2E_BASE_URL` contains
  `calendar-test`. Confirm the guard cannot be bypassed into production.

**Axis B brief:**

- Assertions that cannot fail — `expect(x).toBeDefined()` on a literal, snapshot tests
  with no meaningful content, `await`ed promises with no assertion after.
- Specs that mutate the six seeded assessment types or the four seeded remark criteria.
  `CLAUDE.md` forbids this — other specs and seeded score rows depend on them.
- Sidebar state: any spec that clicks or reads a sidebar row must seed
  `mochi_sb_collapsed_v1='[]'`, or it breaks under collapsed-by-default.

**Context:** `docs/test-run-2026-08-14.md` is today's run record — read it first for
current state. Commit `fb9fb76` took the staging suite "from 24 failures to none", so the
suite is green; this slice asks whether green means covered.

**Output:** `docs/review/08-tests.md`.

## Rules for every slice

1. **Two axes, separately reported.** Never merge, never rerank across them.
2. **Documented repo standard beats the smell baseline.** Where the repo endorses
   something the baseline would flag, suppress the smell.
3. **Baseline smells are always judgement calls** — "possible Feature Envy", never
   "violation".
4. **Skip what tooling enforces** — but remember `npm run lint` does not cover `server/`,
   `mobile/`, `e2e/`, `test/` or `video/`.
5. **Quote the evidence.** Every finding cites `file:line` and quotes the hunk. Every
   standards violation cites the standard: which file, which rule.
6. **Re-grep before trusting a line number**, including the ones in this plan.
7. **Never run a test suite.** Static checks only (`typecheck`, `lint`, `check:i18n`,
   `format:check`). If a finding needs a suite to confirm, say so in one line and leave
   the decision to the repo owner.
8. **Findings only — no fixes.** This plan produces a reviewed, triaged list. Fixing is a
   separate pass against the triage table, so the reviewer's judgement and the fixer's
   judgement stay independent.
9. **Under 400 words per axis per slice.** Length is not thoroughness. The triage table
   is what gets acted on.
