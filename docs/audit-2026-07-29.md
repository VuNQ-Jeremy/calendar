## Phase 1 — `GestureHandlerRootView` is never mounted

**Severity: critical. Decision: root wrapper.**

### What happens

| Screen | Path | Result |
|---|---|---|
| More → System Config | `mobile/app/(app)/config.tsx:193` renders `DragReorderList` | full-screen `Render Error` |
| Flashcards → topic → Flip cards | `mobile/games/FlipGame.tsx:80` (render), `:283` (GestureDetector site) | full-screen `Render Error` |

Both throw:

```
GestureDetector must be used as a descendant of GestureHandlerRootView.
Otherwise the gestures will not be recognized.
  at mobile/components/DragReorderList.tsx:94 (DragRow)
  at react-native-gesture-handler/src/handlers/gestures/GestureDetector/index.tsx:93
```

The flip game matters more than it looks: a student's entire reachable surface is Flashcards +
Profile, so this is their primary feature.

### Root cause

```bash
grep -rn "GestureHandlerRootView" mobile/app mobile/components mobile/ui mobile/games
# -> no matches
```

`mobile/app/_layout.tsx:1` has only the legacy side-effect import,
`import 'react-native-gesture-handler'`. That was sufficient under the old architecture; with RNGH v2
on RN 0.86 the tree must actually be wrapped. Exactly two files use `GestureDetector`
(`components/DragReorderList.tsx`, `games/FlipGame.tsx`) and both are reachable from the UI.

### Why production never crashed

The throw is `__DEV__`-guarded — RNGH's own line 92:

```ts
const rootViewContext = useContext(GestureHandlerRootViewContext);
if (__DEV__ && !rootViewContext && !isTestEnv() && Platform.OS !== 'web') {
  throw new Error(...);
}
```

So a shipped EAS build does **not** crash. It renders, and the gestures simply never fire:
drag-to-reorder assessment types does nothing, and the flashcard swipe does nothing. That silence is
why this survived a release. It also means `docs/mobile-parity.md` is currently wrong — it lists
"Swipe gestures in the flashcard games" under *Things the phone does that the web cannot*.

### Fix

In `mobile/app/_layout.tsx`, add the named import (keep the line-1 side-effect import) and wrap the
returned tree of `RootLayout` — currently lines 84–96, `SafeAreaProvider → ThemeProvider →
PersistQueryClientProvider → LanguageProvider → AuthProvider → StatusBar + Gate`:

```tsx
import { GestureHandlerRootView } from 'react-native-gesture-handler';

// ...

return (
  <GestureHandlerRootView style={{ flex: 1 }}>
    <SafeAreaProvider>
      {/* existing tree unchanged */}
    </SafeAreaProvider>
  </GestureHandlerRootView>
);
```

A root wrapper rather than per-call-site wrappers, so the next `GestureDetector` added anywhere does
not reintroduce this.

This exact change was applied during the audit, hot-reloaded, and System Config rendered completely;
it was then reverted, Metro's cache cleared so the bundle matched disk, and the flip game threw
again. Both directions are confirmed.

### Shipping

JS-only, so it reaches installed preview APKs over the air:

```bash
cd mobile && npm run update:preview
```

**No `runtimeVersion` bump and no rebuild** — per the cost table in
`docs/mobile/phase-7-dev-loop-and-delivery.md`, only native changes need those.

### Acceptance

- [ ] System Config opens with no Render Error — *pending device*
- [ ] Drag-reorder an assessment type and confirm the order **persists server-side** (`GET /api/assessment-types` returns the new order, or re-open the screen) — *pending device*
- [ ] Flip game opens, a swipe advances the card, and a finished round **records results server-side** (`POST /api/flashcards/results`; the topic's Results tab reflects it) — *pending device*
- [x] `cd mobile && npm run typecheck && npm run bundle` both pass — typecheck reports only the
      pre-existing expo-router typed-route errors in `materials/index.tsx` and `people/index.tsx`
      (confirmed present on a stashed tree, unrelated to this change); the bundle exports clean
- [x] `docs/mobile-parity.md`'s swipe-gestures line is accurate for whatever state ships — the fix
      ships, so "Swipe gestures in the flashcard games" is now true and stays as written
- [x] implemented

## Phase 4 — `invm_no_class` missing key + i18n guard script

**Severity: minor. Decision: fix the key, add the checker as a repo script, no CI gate.**

### What happens

Web → People → **Generate invite** → the "Link to class (optional)" dropdown renders the literal
string `invm_no_class`. Mobile shows "No class" correctly (it uses its own chip row).

`src/screens-manage/people.tsx:1041` calls `t('invm_no_class')`, and that key exists in **neither**
locale of `shared/i18n/strings.ts` — every sibling `invm_*` key does (en ~381–388, vi ~1030–1037,
including `invm_link_class` right next to where it belongs). `t()` falls back to returning the key.

### Fix

```ts
// shared/i18n/strings.ts — en block, beside invm_link_class
invm_no_class: 'No class',

// vi block, beside its invm_link_class
invm_no_class: 'Không có lớp',
```

### The sweep behind it

The whole repo was swept for this class of bug; **this is the only real one**. Three other
"undefined" hits are false positives — dynamic prefixes, not missing keys:

| Apparent key | Actually | Site |
|---|---|---|
| `role_` | `t('role_' + String(r).toLowerCase())` | `src/auth.tsx:38`, `src/screens-manage/people.tsx:61` |
| `rel_` | `t('rel_' + String(r ?? 'guardian').toLowerCase())` | `src/screens-manage/people.tsx:60` |
| `feat_` | `t('feat_' + f.key + '_title')` | `src/instructions.tsx:48` |

Vietnamese dates are also fine: `months` / `monthsShort` / `dow` / `dowMon` don't live in the locale
blocks at all — they resolve through a separate `CAL[lang] ?? CAL.en` lookup at
`shared/i18n/strings.ts:66-69`.

### Guard script

Add `scripts/check-i18n.mjs`, a cleaned-up port of the audit checker:

- parse the `en` and `vi` key sets out of `shared/i18n/strings.ts` (the `vi` block starts at the `vi: {` marker);
- walk `src/`, `app/`, `mobile/`, `shared/` for `t('key')` / `t("key")` / `` t(`key`) ``;
- skip `node_modules`, `.expo`, `android`, `ios`, `dist`, `build`, `.react-router`, `test-results`, and skip any compiled `.js` that has a sibling `.ts`/`.tsx` (the repo currently carries ~180 such strays);
- report **referenced-but-undefined** keys and **en keys missing from vi**;
- allowlist the dynamic prefixes `['role_', 'rel_', 'feat_']`.

Wire it as `"check:i18n": "node scripts/check-i18n.mjs"`. Deliberately **not** added to `lint` or CI —
run it by hand.

### Out of scope: 89 unused keys

The sweep also found 89 keys defined but never statically referenced. **Do not prune them here.**
Many are dynamic-prefix targets (`type_*`, `cat_*`, `bh_*`, `att_*`, `cfg_sb_*`, `cfg_tb_*`,
`role_*`), and others are reached indirectly — mobile's login passes an i18n key through a variable
(`setError('auth_wrong_creds')` then `t(error)`), which no static scan can see. Record the list as
backlog; pruning deserves its own pass.

- [x] The unused-key list is captured as backlog — [docs/i18n-unused-keys.md](i18n-unused-keys.md).

## Phase 6 — Touch targets below the repo's own 48dp floor

**Severity: minor. Decision: hybrid on mobile (visual bump for chips, `hitSlop` for icons); 44px minimum on web.**

`docs/mobile-parity.md` says every control is "built against the 48dp floor (`theme.TOUCH`), but that
is construction, not observation." It is now observed — `mobile/theme/index.ts:57` does define
`TOUCH = 48` — and it is not applied everywhere.

### Measured

At 420dpi, 48dp = 126px. Figures come from each **clickable** node's own bounds.

| Client · screen | Control | Measured |
|---|---|---|
| Mobile · Flashcards | topic Edit / Delete | **36 × 36 dp** |
| Mobile · Flashcards | Download | **85 × 18 dp** |
| Mobile · Profile | avatar colour swatches (×6) | **40 × 40 dp** |
| Mobile · Calendar | Agenda / Month / Day | **40 dp tall** |
| Mobile · People, Homework, Feedback | tab and filter chips | **40 dp tall** |
| Mobile · Materials, Assessment | filter chips | **44 dp tall** |
| Mobile · Homework rows | Grade / Edit / Delete | 48 × 48 dp ✅ |
| Web · every modal | Close (×) | **36 × 36 px** |
| Web · New event, New topic | inline icon button | **34 × 34 px** |

**Caveat, stated rather than papered over:** widths of partially-scrolled rows are truncated by the
viewport, so treat *heights* as the reliable figure. The pattern is consistent — primary buttons hit
48dp, chips and icon buttons do not.

### Fix

- **Mobile chips / segments / list tabs** (the 40–44dp-tall family — `ChipSelect`, segmented
  controls, tab rows): set `minHeight: theme.TOUCH`. Visual, and therefore verifiable by re-running
  the dump sweep.
- **Mobile icon-only controls** (36dp `IconButton size="sm"`, 40dp avatar swatches, the 18dp-tall
  Download pressable): extend `hitSlop` to reach ≥48dp effective. No visual change.
  **`hitSlop` does not change the bounds `uiautomator` reports**, so this half cannot be confirmed by
  the sweep — it needs code review plus a tap test.
- **Web icon-only buttons**: CSS `min-width: 44px; min-height: 44px`. 44 rather than 48 to keep modal
  headers from growing noticeably; 44 is the W3C/Apple floor.

### Acceptance

- [ ] Re-run the dump sweep (per-node `text` / `content-desc` / `clickable` / `bounds`, with a foreground-package assertion, scale 2.625): every control given a **visual** bump measures ≥48dp — *pending emulator*
- [ ] Tap test: taps ~4dp outside the drawn edge of each `hitSlop`-fixed control register — topic Edit/Delete, an avatar swatch, Download — *pending device*
- [ ] Web: DevTools box inspection at 390px shows ≥44px on modal Close and inline icon buttons — *pending browser*
- [x] implemented

### What was actually changed, and what turned out to be already correct

Half the `hitSlop` half of this phase was **already done in the code** — the audit measured drawn
bounds, and `uiautomator` cannot see `hitSlop`, which is exactly the caveat the phase itself
flagged. Read before assuming a regression:

| Control | Found | Action |
|---|---|---|
| `ui/IconButton.tsx` `size="sm"` (topic Edit/Delete, word Edit/Delete, play-audio) | 36dp box **plus `hitSlop={(48-36)/2}`** = 48 effective | none needed |
| `ui/ColorPicker.tsx` + `profile.tsx` avatar swatches | 40dp box **plus `hitSlop={4}`** = 48 effective | none needed |
| `components/TokenSearch.tsx` selected-token chip | 36dp **plus `hitSlop={6}`** = 48 effective | none needed |
| Flashcards Download pressable | 18dp tall, `hitSlop={12}` → **42 effective, genuinely short** | `hitSlop` → 15 |
| `components/ChipSelect.tsx` chip | `minHeight: 44` — the comment claimed "the row is the target", but the row is not clickable, the chip is | `minHeight: th.touch` |
| `ui/Tabs.tsx` segment (Calendar Agenda/Month/Day, People, Homework, Feedback, Assessments tabs) | `minHeight: 40` | `minHeight: th.touch` |

Those two shared components cover **every** 40–44dp chip and tab row the audit listed — there were
no one-off inline chip implementations to chase.

On the web, `.mochi-icon-btn` was already 44px; only `.is-sm` dropped it to 36. The base rule now
carries a `min-width`/`min-height: 44px` floor so no future caller can undercut it, and `.is-sm`
no longer shrinks the box. Three further sub-44px **clickable** boxes were found by sweeping
`cursor: pointer` rules and fixed alongside, since they are the same defect:
`.m-datepicker__day` (34→44), `.m-datepicker__nav` (30→44), `.m-swatch` (34→44),
`.m-select__option` (38→44 min-height), and on /config `.colorrow__swatch` (32→44 tall) and its
`input[type='color']` (36→44 tall). The datepicker popover grows to ~344px wide, still inside 390px.

## Phase 7 — No-action records

Nothing to implement. Kept here so the audit is complete in one place.

### Verified safe — a `PATCH` cannot silently wipe columns

Worth recording for every collection, not just classes. The suspicion: the web never sends
`schedule`, `ClassInput.schedule` has `.default([])`, and `server/services/classes.ts:111` guards
with `if (input.schedule !== undefined)` — so a full Zod parse would inject `[]`, pass the guard, and
delete every row.

It doesn't. `server/api/handler.ts:127-148` uses a bespoke `parsePatch` for exactly this reason:

> Uses parsePatch rather than `schema.partial()` because Zod still applies `.default()` for absent
> keys, which would silently overwrite columns the caller never mentioned — e.g. toggling `favorite`
> resetting `type` to its default.

**Confirmed against production:** room and a schedule slot were set on the phone, the class was then
renamed on the web, and both survived byte-for-byte.

### Open question — student profile has no Phone field

### Checked clean

- **Student role is genuinely at parity.** Both clients land a student on `/flashcards`; web
  redirects every staff route there, mobile hides those tabs via `href: null`
  (`mobile/app/(app)/_layout.tsx`), and promotes Profile to a tab because "for a student it IS a tab
  — they have nowhere else to go." Verified live on both. No write access to topics on either.
- **CRUD verbs are at parity** for classes, students, homework, materials, assessments, flashcard
  topics and words, assessment types and feedback. Only the shape differs: web puts Edit/Delete icons
  on rows and edits in a modal; mobile has the same row icons but pushes a full screen, and puts
  class delete as a full-width destructive button at the bottom of the editor.
  `mobile/app/(app)/classes/index.tsx:15` explains why the phone went full-screen — the modal "held a
  roster, a schedule, a stats row and a material picker, none of which fit in a sheet." Invites have
  no update on either client by design.
- **No horizontal scroll** on any of the 11 web routes at 390px.
- **Invite roles diverge deliberately, and mobile is the stricter client.** Web offers a **Parent**
  role that provably cannot sign in (`server/services/auth.ts` — "parent accounts remain
  unsupported"); mobile offers Student/Teacher only and explains itself via `invm_no_parent_note`,
  a string used only by mobile. The web's version of this modal is also where P4's bug lives.
- **Mobile-only conveniences** not previously recorded: a "Search people…" field on People and
  "Search materials…" on Materials (the web routes have no text input at all), and a
  "1 of 5 complete / 20%" progress bar on Homework.

### Lessons for the dev loop

Three things that cost time during this audit and will cost it again.

1. **Metro can serve a stale bundle after a `git checkout`.** The file watcher missed a revert, so
   the running app kept the old module and a reverted fix appeared to still work. Only
   `npx expo start --clear` guaranteed bundle == disk. If a change seems not to take effect — or a
   revert seems not to — check for a rebundle line in Metro's output before believing the app.
2. **`uiautomator` dumps hide icon-only buttons** unless you read `content-desc` per node. Such nodes
   have `text=""`, so any parser that prefers `text` and skips empties silently drops every Edit,
   Delete and Grade icon. This briefly made mobile look like it lacked deletes it has.
3. **PowerShell flattens nested arrays** — `@(@(108, 2250))` becomes `@(108, 2250)`, so
   `$coords[0]`/`$coords[1]` yield the first value and `$null`. That produced one-argument
   `adb shell input tap` calls that failed silently and drove the Android launcher instead of the app.
   Pass coordinates as strings (`"108 2250"`) and assert the foreground package before trusting any
   dump.
